# T1.6 コマンド（抽出・提案・評価を通しで回す）

- 状態：完了（2026-10-15）
- 段：1　依存：T1.4

## 目的
人が1つのコマンドで、接続 → 抽出 → 提案 → 検証 → 評価を回せるようにする。

## やること
- `mandara` コマンド（Application 層）：`extract`（カタログ → 主張）、`propose`（主張 → OM）、`validate`、`eval`、通しの `run`
- 範囲（スキーマ）の指定。接続情報は環境変数
- 実行の記録（入力のハッシュ、版、提案数）を `work/<source>/runs/` に書く（仕様 6.3、6.6.5）

## 完了条件
- AW に対して `run` が通り、OM・主張・評価・実行の記録が `work/adventureworks/` に出る

## 使い方
```
mandara run --source adventureworks --schema humanresources --schema person --schema production \
  --schema purchasing --schema sales --gold evals/datasets/adventureworks/gold/ontology
mandara extract  --source S --schema …      # カタログ → 主張台帳
mandara propose  --source S                 # 主張台帳 → OM
mandara eval     --source S --gold DIR      # OM ↔ 正解
mandara validate DIR                        # OM の検証（違反があれば終了コード 1）
```
接続は `--conninfo`（libpq の接続文字列）か、libpq の環境変数（PGHOST、PGDATABASE など）。秘密はリポジトリに書かない。

## 実装で決めたこと
- Application 層（mandara.app.pipeline）にユースケース（extract / propose / evaluate / validate / run）。CLI は呼ぶだけで、コネクタを組み立てる場所（composition root）
- 範囲は主張台帳の中（claims/scope.json）に、台帳と同じ置き換えで書く（範囲と主張が食い違わない）
- 実行の記録は開始時に running で書き、段ごとの完了、成功・失敗（失敗した段と理由）を書き足す。正解と比べたときは、正解のパスと内容のハッシュも書く
- 想定内の失敗（データ、ファイル、操作）は名前付きの例外にして、CLI は1行で表に出して終了コード 2。それ以外（モデラーの出力が検証を通らない、pydantic の ValidationError など）はバグなので握りつぶさずに落とす
- 色は端末のときだけ。NO_COLOR を尊重する
