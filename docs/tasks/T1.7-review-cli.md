# T1.7 レビュー CLI

- 状態：完了（2026-10-15）
- 段：1　依存：T1.6

## 目的
提案に人が答え、`approved` / `rejected` を OM に書き込む。UI のレビュー画面（T3.5）の前の、最小の承認経路。

## 背景
仕様 9.3（問いの形式、根拠を3行まで、影響順、束で承認）、3.3（approved を書けるのは人だけ）。

## やること
- 提案を問いの形で1件ずつ出す（例：「salesorderdetail.salesorderid は salesorderheader を参照しますか？」）。根拠の主張を3行まで添える
- 回答：はい / いいえ / 飛ばす。`reviewed_by`（git の user.name か引数）と `reviewed_at` を書く
- 確信度が閾値以上の提案は一括承認できる
- 書いた結果を検証（4.5）に通す

## やらないこと
- 「別の意味」の回答と、回答の主張化（T3.6）

## 完了条件
- AW の提案を CLI で承認・却下でき、結果が検証を通る
- 法則テスト：レビューは status と reviewed_* 以外を変えない

## 使い方
```
mandara review --source adventureworks --reviewer alice              # 1件ずつ答える
mandara review --source adventureworks --reviewer alice --bulk 0.95  # 一覧を見せて、確認してから一括承認
```

## 実装で決めたこと
- 問いは未判断の注釈ごとに1つ。並びは 表（関係の多い順）→ 関係・辺 → 列 → enum の値。根拠は3行まで
- 種類が未決の表は、承認するときに人が種類を選ぶ。答えで検証が通らなくなるなら（grain の無い表を event にする、など）、その答えは拒否して選び直してもらう
- 判断は答えるたびに書く。書く側の境界（write_reviewed_ontology）で、判断以外の変更（項目、注釈の増減、並び順、語彙、判断済みの判断、reviewed_* の欠けや書き換え）を拒否する
- 一括承認は「候補の一覧 → 確認 → 承認」。閾値は 0.95 以上だけ（下げてよいか、一括承認を記録で区別するかは仕様 15.2 で未決）。種類の選択が要る表は含めない
- 注釈の場所は修飾名の規則で組み立てる（部品に "." があっても重ならない）
