## 第一弾：値の包含から結合を推定する（規則 3a。2026-10-18）

### 作り
- **測る**（抽出器 `extractors/joins.py`。純粋。値を読むのはポート `source/inclusion.py` の InclusionReader）：
  - 参照先：1 列のキー（主キー、または NULL の無い列の一意）
  - 参照元：表の列で、キーと型族が同じもの（smallint の列が integer のキーを指せる）
  - 安い順に足切りする。足切りで落とした組は主張にせず、数だけを実行の記録に残す：
    1. 型族
    2. 異なる値の数と範囲（比べられる値の組だけ。タイムゾーンの有無が違う日時や NaN は比べない）
    3. 見本の重なり（先頭 50 値に重なりが無い組を落とす）
  - 残った組は全部数える。包含が成り立たない組も、否定の証拠として主張にする（`included_in`）
  - 参照先のキーの値の数は、包含と同じ問い合わせ（同じスナップショット）で数える
- **決める**（モデラー `modeler/joins.py`。純粋）：
  - 候補は、包含が 100% で、名前の手がかり（4 段）が 1 以上の組
  - 表の 1 列の主キーが別の表を指すのは、名前が完全に一致するときだけ
  - 1 列に参照先は 1 つ。並べる順は、名前の強さ → 最も狭い包含先 → ハブ（名前で多くの表から指される表）
  - 値の集合が同じ表どうしの両向きは、ハブの弱い側が次の候補を選ぶ
  - 確信度は 0.7〜0.85（宣言より低い）。人のレビューに回る。根拠の 1 行は「値の包含 · personid の 19,119 値のすべてが…」
- **後段**：判断モデルと LLM には、参照とみなした `included_in` だけを「参照」として渡す
  - 型 `InferenceClaims` で守る。絞っていない測定は、型エラーで渡せない
  - 主キー共有（is-a の手がかり）の被覆は、事実だけで決めた候補で測る（包含 100%・両側の列の名前が同じ・主キーを共有）。
    選び方の版に、主張台帳を依存させない
- **評価**：`mandara eval-joins --truth dbname=adventureworks`。元の DB で宣言されていた外部キーとの再現率・適合率
- **法則（テスト）**：
  - InclusionReader の共通の法則（`tests/inclusion_laws.py`）。偽物と PostgreSQL の両方に当てる。型をまたぐ等値、文字列、uuid を含む
  - 足切りの健全さ（整数と日付）、選び方の法則（1 列に 1 つ、包含 100%、循環なし、入力の順に依らない）
  - `claims_for` の過不足、宣言との重複なし、AdventureWorks での再現率 95% 以上・適合率 90% 以上

### 3b：名前の手がかりが無い包含を、判断モデルが決める（2026-10-18、ユーザーと合意）
- **事実を足す**：整数の列の `included_in` に、列の値の範囲の幅 `value_span`（最大 − 最小 + 1）と、その範囲にあるキーの値の数
  `target_values_in_span` を載せる。同じ問い合わせの中で数える。抽出器は `joins 0.2`
  - 主張の形に「持っても持たなくてもよい」フィールド（`Shape.optional`）を足した。整数でない列は持たない
- **偶然の確率**はモデラーが数から計算する（解釈なので主張にしない）：C(K, d) / C(S, d)
  - d は列の値の数、K は範囲にあるキーの値の数、S は範囲の幅。項ごとに log1p で足すので、0 を超えない
  - 範囲は、キー全体ではなく列の値の範囲にとる。1 から始まる数量や区分は範囲の下の方に偏るので、キー全体の詰まり方で見ると
    偶然を過小に見積もる（最初の版でこれを踏んだ：`sickleavehours → address` が 10⁻¹¹ になった）
  - 結果：`componentid → product` は 10⁻¹³¹。数量・区分の列はほぼ 1（証拠にならない）
- **問う列**（`mandara.modeler.nameless_joins`）：包含 100% の測定を持つ列のうち、次のどれでもない列
  - OM の 1 列の関係の参照元
  - 宣言された外部キーの列（範囲外を指すもの、複合の一部も含む）
  - 表の 1 列のキー（主キー・代替キー）
- **問い方**：表ごとに 1 回、判断モデルに問う。表の分類の前に、全部の表について問う。選んだ参照は、分類と LLM に参照として渡る
  - 選択肢は、偶然の確率が低い順（同じなら最も狭い包含先）に 5 個まで ＋「参照ではない」＋「決められない」
  - 材料は表の主張（列・コメント・キー）と、候補ごとの数
  - 問いに書く事実は、主張で確かめたものだけ：宣言が無いこと、名前がどの候補も指さないこと
- **確信度**：判断モデルの確率。ただし 0.7 を超えない（名前の手がかりがあるものより上にしない）。閾値 0.6 未満と「決められない」は、
  理由つきで記録だけする
- **記録**：実行の記録の `refine.nameless`（表ごとの答え、確率、根拠の主張 ID）。予算で止まったら、残りの表は `not_reached`

#### column_types の落ちの中身と、真偽値の列（2026-10-18、ユーザーと合意：案 A）
- 落ちた 20 列のうち 14 列は enum を作れなくなったこと。enum の値の根拠はコメントか CHECK に限っていて（C6：値の集合をデータから
  取らない）、コメントが無いと根拠が無い
  - フラグ 7 列（`salariedflag` など）：真偽値の型族に当てられる値の型が enum しか無いので、意味型そのものが付かない
  - 文字のコード 7 列（`gender`、`status` など）：`code` に落ちる（意味としては誤りではない）
  - 残り 6 列は確信度の不足と命名の揺れ
- **直したこと（案 A）**：真偽値の列の値の集合 {true, false} は型族が決めるので、型の主張（`typed_as`、型族 boolean）を
  enum の値の根拠にしてよい。データは見ないので C6 と両立する
  - 根拠にできるのは、値がちょうど true / false のときだけ（`om/value_types.py` の `is_boolean_value_set`）
  - 値が真偽値の意味型は、型族 boolean の列にだけ当てる（`misfit`。LLM の答えと、同じ意味の伝播の両方）。
    当てる側で見るのは、OM の語彙は表をまたいで使い回されるため（レビューの指摘）
  - 命名の問いは、コメントが無ければ型の主張を挙げ、ラベルは列名から読むように変えた
- 結果（段 2、LLM あり、¥14.57）：column_types 107 → **116**/141（段 1 は 124）。真偽値の 13 列のうち 11 列に意味型
  - 残るのは文字のコード 6 列（`code` に落ちる。案 B：観測値を根拠に認めるかは T2.3 で設計する）、確信度の不足、命名の揺れ
- 残る課題（レビューの指摘。仕様の判断が要るので未着手）：
  - 型の主張が裏付けるのはコードの集合だけで、ラベル（true = 自社で作る）は列名からの推測。いまは値の根拠が型の主張なので、
    レビューする人は根拠の種類で見分けられるが、メタモデルとしてコードとラベルの根拠を分けて持つかは未決（C6）
  - コメントのある真偽値の列でも、型の主張だけを挙げた答えを受け付ける。コメントや CHECK の根拠が、どの列のものかも問わない
    （既存。値の根拠と列が結びついていない）
- 3b の揺れ：この回は多相の `transactionhistoryarchive.referenceorderid → workorder` を確率 0.63 で足した（前の回は 0.49）。
  閾値の近くの答えは回ごとに変わる。1 列の結合の適合率 96% → 95%

### 既知・決めたこと
- **主張の ID**：`included_in` は数を内容に含むので、行が変わると ID も変わる（その時点の事実として正しい）。関係の ID は出所の
  場所から作るので変わらない。将来、主張 ID で判断や差分を引くなら、測定の時点（valid_at）の持ち方を決める
- 複合キーへの参照（`salesorderdetail → specialofferproduct`）はまだ測らない
