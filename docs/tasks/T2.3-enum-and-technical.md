# T2.3 enum 候補と技術列の検出、監査 TS による domain / event の根拠

- 状態：未着手
- 段：2　依存：T2.1

## 目的
低基数の列を enum 候補に、監査列（modifieddate、rowguid）を technical に寄せる。

## 背景
仕様 6.7.1（低基数の列は関係ではなく enum）、4.1（role: technical）

## やること
- 基数の閾値で enum 候補を出す。値の一覧は観測値（observed）として持ち、値の集合の根拠にはしない（C6）
- CHECK 制約の値の一覧（T1.3）と突き合わせる
- 名前・型・既定値（now()、uuid の生成）から technical の候補を出す
- 監査 TS（作成日時・更新日時）の関係を、表の種類（domain / event）の根拠の主張にする（2026-10-16 の提案）
  - 作成と更新の TS があり、行ごとに異なる値が入っている → 行が更新される → domain 寄り
  - 作成 TS しか無い、または更新 TS があっても作成と同じ値しか無い → 追記だけ → event 寄り
  - 決め手にはせず、中くらいの重みの根拠にする。一括で投入したマスタは作成 = 更新のままで event に見える。
    AdventureWorks は一括投入のサンプルで、列も modifieddate だけ（作成 TS が無い）なので、この根拠はほぼ効かない
  - 行を見ないと分からないので、OM の静的な規則ではなく、データについての主張（仕様 6.6）として出す

## 完了条件
- 正解 OM の enum 16 意味型のうち、候補に入る数を測る
- 監査 TS の根拠が、どの表に、どちら向きに出たかを記録する（AW では効かないことの確認を含む）
