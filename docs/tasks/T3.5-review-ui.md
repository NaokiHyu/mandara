# T3.5 レビュー画面

- 状態：完了（第一弾、2026-10-15）。結果の予告と衝突の選択は後続（下記）
- 段：3　依存：T1.7、T1.8

## 目的
提案に問いの形で答える Web 画面。

## 背景
仕様 9.3

## やること
- 問いの形式、根拠 3 行、影響順、束で承認、衝突の選択、承認の帰結の予告
- 書き込みは CLI と同じ経路（同じ Application のユースケース）

## 完了条件
- CLI と画面で同じ結果になる（tests/test_review_api.py の性質テスト：同じ答えの列を CLI の経路と API に当てると、同じ OM のファイルになり、失敗も一致する）

## 使い方
```
mandara serve --reviewer alice --gold adventureworks=evals/datasets/adventureworks/gold/ontology \
  --connect adventureworks dbname=adventureworks
cd ui && pnpm dev    # http://127.0.0.1:5173/?ontology=work:adventureworks&view=review
```
- キー：Y 承認、N 却下、S 飛ばす、D / R / E / V 種類を選んで承認（種類が未決の表）、J / K 移動（CLI と同じキー）
- 一括承認：候補（確信度 ≥ 0.95、種類を選ばなくてよいもの）の一覧を見てから承認する
- 右側に問いの表の詳細（答えると読み直す）。「表をグラフで見る」でオントロジーの画面へ

## 実装で決めたこと
- 契約は①に足した（ReviewQueue / ReviewQuestion / EvidenceLine / ReviewAnswer / BulkApproval、enum ReviewSubject / ReviewDecision）。
  UI は review.schema.json で応答を検証し、API は要求を①から生成した pydantic の型で検証する
- 問いの並び、根拠の行数（3）、一括承認の候補は Domain（mandara.review.decisions）が決める。画面は並べ替えない
- 列の問いは、ドメインが付いていればその意味（型、説明、単位）を問う。関係の問いは役割も添える
- 書けるのは work の OM で、`serve --reviewer` のときだけ。無ければ問いは読めるが書けない（画面に理由を出す）。正解 OM はレビューしない（409）
- 書く要求は application/json だけ（フォームの送信で書かせない）。Origin があればこの機械（127.0.0.1 / localhost）のものだけ。
  書き込みは1つずつ（ロック）
- 当てられない答え（検証を通らない、など）は 409 で理由を返し、画面はそれを出して選び直してもらう
- スモーク（scripts/check.sh）は使い捨ての作業領域（規則だけの提案）を --reviewer smoke で立て、答える → 一括承認 →
  オントロジーの画面に承認が出る、までを実際に通す。work/ には触らない

- 書いた後に問いの列を作り直せなかったときは、「書いた」と分かる形（written: true）で返す。画面は答え直させない
- 制約：書き込みの直列化は serve のプロセスの中だけ。同じ作業領域に CLI の mandara review を同時に走らせない（作業領域のロックは未実装）
- CLI と画面で同じなのは、ユースケース（答え → OM）まで。キーの対応（Y / N / S / D R E V）は両側で同じにしてあるが、突き合わせるテストは無い
