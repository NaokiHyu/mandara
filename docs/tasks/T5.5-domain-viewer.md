# T5.5 ドメインビューワ

- 状態：第一弾（2026-10-17）
- 段：5　依存：T3.5（承認）

## 目的
承認済みの OM から、ドメイン（集合。表のイメージ）とインスタンス（個。行のイメージ）を見せる。値はソースをその場で読む（ゼロコピー）。

## 決めたこと（2026-10-17 合意）
- ドメイン：承認済みの domain / event の表で、主キーのあるもの。relation の表はドメインにせず、n:m のリンクとしてたどる。
  ドメインにしない表は理由とともに一覧に出す
- 集合：検索（意味型が文字・コード・識別子・enum の列と、キーの部分一致）。50 件まで
- 個：値（技術列を除く）、参照先へのリンク（n:1。found / null / missing を区別）、近隣の集まり
  （参照してくる行 1:n、relation の表を挟んだ先 n:m。20 件まで）。たどらなかった関係は理由つきで返す
- 行を読むポート（mandara.source.records）は Domain、PostgreSQL の実装は Adapter。一致は列の型で比べ、キーは往復できる
  キーの文字列（key_text）で持つ（表示の文字列とは別）
- 表示：列の encoding のコーデックがあれば意味の値にしてから表示する（geography → 緯度・経度）。enum は語彙のラベル
- 画面：view=domain。URL（table と key）で場所を表し、たどった道（パンくず）で戻れる

## 第二弾（2026-10-18）
- n:m の集まりは relation の行ごとに1つで、つながりの属性（relation の行の値。参照の列、技術列、代理キーを除く）を添える。
  例：従業員 → 部署（所属の開始日・終了日）。期間つきの所属の表（employeedepartmenthistory）は、推論で relation（辺）になった
  （種類の問いに主キーの組み立てを事実として添えた。T3.8 の続き）
- 見出しの列が無い表は、主キーを共有する is-a の上位の同じキーの行の見出しを借りる（従業員 → 人の名前）。
  見出しの出どころを label_source（own / borrowed / borrowed_missing / key）で返し、壊れた借用は画面に印を出す
- 検証（仕様 4.5）を通らない OM は見せない（is-a の循環などで借用が終わらなくなるため）
- 1 つの要求の中で同じ読みを1回にする（同じ先が何度も出る n:m、見出しの借用）
- 色：ドメインのカテゴリ（エンティティグループ）ごとの色。名前の順に割り当て、グラフ・一覧と同じ。アイコンは形（文字）が種類、色がカテゴリ
- 識別の列（主キー、見出し、自然キー）は高コントラストの白（--text-key）

## 第三弾（2026-10-18）：近隣の集まりの見せ方
- browse.group_view：出来事の時刻があり 30 件超 → 時系列、期間の列 → 期間の帯、10 件以下 → 一覧、それ以外 → 集計の頭出し
- 集計は加法性から（measure_plan）。半加法は全体では集計せず、最新の時点の行だけで合計する（latest.snapshot）。
  単位の列の値が混ざれば合計しない（理由を skipped_measures に）。尺度は 3 個まで。一覧の見せ方では集計しない
- 時系列は行の無い区切りを 0 件で埋める。合計の無い区切りは「値無し」（0 と区別。線を切る）
- 出来事の時刻の列の値が日付でなければエラー（OM とソースの食い違いを黙って飛ばさない）
- 時系列の区切りは期間の幅から（62 日以下は日、1890 日以下は月、それより長ければ年。点がおよそ 60 以下）
- 時系列は全幅でインスタンスの上に出す：数字の帯（合計、最新の区切りと前との増減、ピーク）、面グラフ、目盛り、ホバーの値、
  最新の点の強調。最新の区切りが途中まで（最新の日が区切りの最後の日より前）なら増減を出さず「途中」と明示する
- 最新の日（latest）：今日まで届いていれば「今日」、届いていなければ基準日を明示。
  既知：今日は UTC の日付。時刻の列がタイムゾーンつきだと、日付の境界でずれうる。未来の日付があれば最新の日は未来になる
- 集計はポート RecordReader.aggregate でソースに押し下げる（件数・合計・平均・最小・最大を、まとめずに・列の値ごとに・時間の区切りごとに）。
  PostgreSQL の実装と、テストの偽物に同じ法則を当て、両者が一致することも確かめる
- UI：GroupPanel（線グラフと期間の帯は素の SVG / CSS。依存を増やさない）
- 既知：今の work の OM は役割・加法性の付け漏れ・付け間違いが多い（取引履歴に event_time が無い、所属の開始日が event_time、
  受注の金額に加法性が無いなど）。見せ方は OM に従うので、OM が直れば線グラフや帯になる。推論の質の問題として別に扱う

## 第四弾（2026-10-18）：集合と、インスタンスの中の集まりは同じもの
- 「B のドメイン」と「A のインスタンスの中の B」は、フィルタの違いだけの部分集合（八百屋 X の野菜 ⊆ 野菜）。
  ユースケースを browse.collection（ドメイン＋任意の親のフィルタ within）に1本化し、インスタンスの 1:n の集まりと同じ
  _subset（見せ方・集計・行の読み方）を使う。契約は GroupProfile の mixin を DomainRows と RelatedGroup の両方が持つ
- 法則（テスト）：集まりの見せ方・集計のすべての項目は、そのインスタンスで絞った集合と同じ。集まりの行は集合の先頭の行。
  部分集合は全体より大きくない。検索は行だけを絞る（件数と集計は検索の前の集合）
- 子の集まりの「この集合 →」は絞り込んだ集合を開く。URL は within_table・within_key・within_relation（3 つそろえる）
- 行の並びはキーまで含めて全順序（同じ時刻の行の並びを決める）。NULL は一致の値にできない（ポートで拒む）。
  親の参照される列が NULL なら、空の部分集合として明示する
- 既知：集合の見せ方と集計は検索のたびに計算し直す（検索に依らないので分けられる）。テストの偽物と PostgreSQL の一致は、
  実データの見本で確かめただけ（生成したデータでの比較はしていない）

## 第五弾（2026-10-18）：n:m も同じ部分集合に。リレーションは控えめに
- n:m の集まりを「つながりの行」から「つながる先の行（重複しない）」に変えた。社員 X の部署 = 部署の集合を
  「X を指す所属の行がある」で絞ったもの。1:n と同じ _subset に、絞りとして Exists（同じソースの別の表につながる行がある。
  準結合）を渡す。ポートの RecordReader に Exists を足し、PostgreSQL は相関副問い合わせ
- つながり自体（relation の行。所属の期間、在庫の数量）は links（LinkGroup。GroupProfile の mixin）に分けた。見せ方の規則は同じ
  （期間の帯、時系列、集計、一覧）で、行は relation の行ごとの先と、その行の値（link_cells）。先の行が無ければ missing、
  先を指す列が NULL なら unlinked に数える（打ち切っていなければ rows + missing + unlinked = つながりの行の数）
- n:m で絞った集合は within に via_relation（relation の表から親への関係）を持ち、links も同じものを返す。URL は within_via を足す。
  Application の入口では WithinChild（1:n）と WithinVia（n:m）の直和
- 表示：relation の表はリンクであって物ではない。ドメインビューワには表の名前もつながりの件数も出さない。つながりの期間は
  先の行ごとの帯（先の行が少なければ帯が行の代わり）、値（数量など）は先の行の横に添える（同じ先に2本なら「 / 」で並べる）。
  「こちらを指す列 から」は、同じ relation の表を2つの側から見る集まり（部品表の組立品と部品）を見分けるときだけ出す
- 群と集合の行の上限は RELATED_LIMIT に固定（引数で変えると、集まりと集合の links が食い違うため）
- 法則（テスト）：n:m の集まりは同じつながりで絞った集合と同じ（見せ方・集計・行・links）。先の行は重複しない。
  Exists は準結合（キー = つながる表の一致する行が指すキー）、件数は find の行の数と同じ（検索と組んでも、値ごと・時間の区切り
  ごとでも）。外と内が同じ表でも取り違えない。PostgreSQL と偽物に同じ法則を Hypothesis で当てる
- 時系列は詰めた形にした（数字の帯1行と高さ 40px の面グラフ。金額は $16.1M の短い表記で、正確な値は title）。時系列の群は
  近隣の列の先頭に置く

## 未決・既知の弱点
- 見出しの列は列の名前からの推定（name、名前が name で終わる文字の列）。契約の label_columns に出している。
  OM の語彙（役割など）で表すかは相談事項
- 1 インスタンスを見るのに、関係の数だけ問い合わせる（n:m の先は1件ずつ。同じ行は1回にした）。集合での一致（In）は未対応。接続は問い合わせごとに開く（プールしていない）
- 検索の部分一致は列を text にキャストするので索引が効かない（大きい表では遅い）
- 意味型の無い列（規則だけの提案）は検索に使わない（キーだけで探す）
- T5.4（LLM が書く表示関数への差し替え）はこの上に載せる
- 代理キー（1列で参照でない relation の表の主キー）は構造からの推定。OM の役割で表すかは相談事項
- 自然キー：この AdventureWorks（PostgreSQL 版）には一意制約がほとんど無く、代替キーが提案されない。白にできるのはキーと見出しだけ。
  データからの一意性（T2.1）で代替キーを提案すれば出る
- 種類の選択肢の言い回し（relation は開始日を含みうる、event は単一の値の変更）は AdventureWorks でしか評価していない
